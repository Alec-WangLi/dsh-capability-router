# 功能说明

这份文件回答一个问题：**这个插件现在到底会做什么、在什么条件下做、有什么代价。**

设计取舍与宿主 API 的实测记录在 [DESIGN.md](../DESIGN.md)；安装与排障在 [INSTALL.md](./INSTALL.md)。

适用版本：v0.20.1 · 宿主 DSH Desktop 0.2.1（`@deepseek-ai/dsh-desktop-runtime` 0.2.1-rc.5）

---

## 一、它插在哪

所有动作都挂在一个钩子上：`agent/pre-step`。它是瀑布式（waterfall）的——先 `await next()` 拿到上游的结论，再决定要不要往 `decision.messages` 末尾追加消息。

```text
用户发一句话
   ↓
agent/pre-step（本插件在这里）
   ├─ 1. 找「真人那句话」（source.kind === "user"）
   ├─ 2. 规则匹配 → 命中哪个专家
   ├─ 3. 命中 → 注入该专家 role.md           （role，默认开）
   ├─ 4. 落空 → 判「像不像一件活」           （gap，默认开）
   ├─ 5. 落空 → 记账到 gaps.jsonl            （gapLog，默认开）
   └─ 6. 每条消息 → 追加一段当轮检查点       （hint，默认开）
   ↓
模型看到的上下文
```

另有一条独立通道 `ctx.systemPrompt.section()`，注入长期原则段（`intake`，默认开）。

工具那条路走的是另一个入口，不经过 pre-step：

```text
模型调 expert(name, {level, approved, phase, project, reopen})
   ├─ 1. 打开专家：接单 → 进 spec，其余只记进「在场专家」   openExpert()
   ├─ 2. 记用户水平（novice / pro）                        setLevel()      v0.20.0
   ├─ 3. 记显式 approved（false 是撤销）                   setApproved()   v0.20.0
   ├─ 4. 重开：deliver → build，记 reopenedAt              v0.20.14
   ├─ 4b. 显式推进阶段（只能往前）                         advancePhase()
   ├─ 5. 不自动确认：approved 只认显式 {approved:true}       v0.20.2
   └─ 6. 落盘 state.json → 按推进后的状态算闸门 note → 下一步的状态卡
```

~~第 5 步只认「`phase` 真的变了」：传了 `phase` 但阶段没动（同一阶段重复交卷、或者被拒），不算确认。~~

**v0.20.2 改了这一步。** 原来是「阶段真变了且已进 build/review/deliver → `setApproved(true)`」，理由是「推进本身就是拍板」。实际跑下来，它把**模型的推进动作**记成了**用户的点头**：模型只要挪一下阶段，状态卡上「方案：待确认」就消失，而用户可能一句话都没说过；审查专家拿到的状态里写着已确认，于是按「已确认的需求」去审，谁也不会觉得自己漏了什么。现在推进阶段只在不确认时补一句提醒，`approved` 保持原值。

## 三、长期原则段（`intake`）

`ctx.systemPrompt.section()` 注册一段系统提示，`order: 5000`（排在 dsh-purge 的尾段 5100 之前）。

内容是「能力路由」的长期协议：需求有空白先问、能力对不上先说、开工前扫技能目录。它的作用是**背景设定**——模型在长对话里回头翻上下文时还能找到依据。

代价：常驻，每轮都在提示里。大概 200 字。

## 四、当轮检查点（`hint`）

每条用户消息后面紧跟一条消息，形状与宿主自己造的用户消息一致：

```js
{
  role: "user",
  id: randomUUID(),
  content: [{ type: "text", text: HINT_TEXT }],
  source: { kind: "capability-router-hint", form: "notice", forPrompt: <该用户消息 id> }
}
```

正文是让模型先归类再动作。**v0.18.0 起是六个出口**（原版只有「提问／命令／报告」三分法，问题见 [REAL-TEST-2026-11-02](./REAL-TEST-2026-11-02.md)）：

| 归类 | 动作 |
|---|---|
| 提问（要答案） | 直接答，不顺手改代码 |
| 命令 · 新活 | 先 `expert("intake")` 收敛需求，再按任务卡分派——**别自己一个人从头做到尾** |
| 命令 · 修 | `expert("debug")` 或对应领域专家，先定位再动手 |
| 报告（是继续） | 接着做，不重新评估已定的事 |
| 收口（要交付） | 先 `expert("review")` 逐条核对；**没跑起来的东西别写「完成」** |
| 拿不准 | 问用户一句，给 2~3 个具体选项，一次问完 |

三个实现细节：

- **怎么认出「真人那句话」**：`source.kind === "user"`。`agent-instructions`、`runtime-context`、`skill-catalog`、`time-context` 也都是 `user` 角色，只能靠 kind 区分。
- **怎么去重**：`forPrompt` + 模块级 `Set`（上限 500，超出只留后一半）。工具调用跑多少步，同一条用户消息只注入一次。
- **注入的消息不进会话历史**：`pre-step` 追加的消息只活在当步上下文里，所以 `hints.jsonl` 是唯一的落地证据。

## 五、专家路由（`experts`）

### 专家包

一个目录就是一个专家：

```text
<包内>/experts/<id>/                          随插件发布（改它要动源码）
<DSH_HOME>/capability-router/experts/<id>/    用户自建或覆盖，同名 id 以内层为准
  expert.yml     name / description / triggers / synonyms / skills / tools
  role.md        命中后注入的角色提示词
  skills/        可选，专家自带技能
```

`expert.yml` 用 YAML 子集解析（`lib/yaml.js`）：扁平 key、标量、一维列表。不支持多行块 `|`/`>`、嵌套映射、锚点——要长文本写进 `role.md`。

校验规则：

| 情况 | 结果 |
|---|---|
| `name` / `description` / `triggers` 任一为空 | 判无效，进 errors，该专家不出现 |
| 缺 `role.md` | 只告警，命中后只注入技能集 |
| 未知字段 | 告警，忽略 |
| 内层同名包坏了 | **直接消失，不退回包内旧版本** |

最后一条是刻意的：少一个专家，比悄悄用错一个专家好。

自带十个：`frontend` 前端工程师、`backend` 后端工程师、`docs` 文档与写作、`debug` 排障工程师、`data` 数据与办公，v0.20.0 新加的三位——`research` 调研专家（`kind: scout`，先查市面有没有现成的，出 `PRIOR-ART.md`）、`reverse` 逆向与安全工程师、`qa` 测试工程师，加两个特殊角色——`intake` 接单专家（`kind: intake`，负责把需求收敛成文档）、`review` 审查专家（`kind: reviewer`，按验收标准收口）。

### 匹配算法

纯规则，不调模型（`lib/router.js`）：

```text
触发词命中    每个 1 + (词长-1) × 0.5   单专家上限 2.5
同义词命中    每个 1.0                  单专家上限 2.0（已当触发词命中过的不重复计）
描述命中      每个 0.5                  单专家上限 1.5

最高分 < 1.0            → miss
≥3 位专家都 ≥ 1.5        → multi（跨领域，列出涉及的几位）
最高分 − 次高分 < 0.35   → ambiguous（列前两名）
否则                    → hit
```

三个设计点：

- **按词长加权**，让「数据库」压过「数据」、「设计文档」压过「文档」。笼统词盖过具体词是最常见的错路由来源。
- **triggers 与 synonyms 分工**：`triggers` 写「这个领域叫什么」，`synonyms` 写「用户会怎么说」（登录、按钮、表单这种）。同义词权重低一档，命中两个才顶得上一个触发词。
- **不重复计分**：同一个词既在触发词表又在同义词表时只按触发词算。这条是修 bug 修出来的——「太慢了」曾因为重复计分把分数从 1.5 抬到 2.5，抢了别的专家。

四种结论都是正常结果：

- **`ambiguous` 不是错误**：分差太小的时候说「像是 A 也可能是 B」，比硬选一个错的好。
- **`multi` 也不是错误**：一句话同时要前端、后端、文档时，唯一正确的答案是「这是三个领域的活」。判据是**双条件**——够多（≥3 位过线）且每一位都明显过线（≥1.5，即至少一个两字触发词的权重）。只数个数会把「给用户表加个索引，查询太慢了」判成跨领域，那里的 `data` / `debug` 只是词面噪音；这条规则是踩了一次 a 集回归（20/20 → 18/20）才收紧的。
- `multi` 时 `verdict.expert` 是 `undefined`：插件不给答案，只描述问题（缺口提示会指向接单专家）。

### 派单书自己点了人（v0.20.17）

派单书长这样：「你现在的身份是**后端工程师**（用 `expert("backend")` 取完整工作方式后照它做事）。项目目录：`C:/work/proj`。任务：把接口补上，前端那边要对接。」

它同时提到后端、前端、接口——`matchExpert` 判它「跨领域」按词面是对的，按语义是错的：**选人这一步已经做完了**。注入「按主领域开工，但交付时把副的那部分一起交」，等于让后端顺手把前端也做了，而前端有它自己的会话和任务卡。真实缺口账本里被判成 `multi` 的 5 条，全是这种派单书。

现在先认身份，两种写法都认：

- `expert("backend")` —— 正则取 id，在目录里查得到才算
- 中文声明「身份：后端工程师」「身份是…」「你是…」——比对时先去掉加粗与行内代码标记（`*` `_` 反引号），否则最常见的 `身份：**审查专家**` 一条都认不出来

认出来就把整句判成 `verdict.kind = "explicit"`：

| 后果 | 行为 |
|---|---|
| 角色注入 | 不注入（角色由派单书自己调 `expert()` 取） |
| 跨领域 / 分不清 / 落空提示 | 全不注入（`gapText` 对 `explicit` 返回 `undefined`） |
| 主次提示 | 不注入 |
| 当轮检查点（`hint`） | **照旧**：这一轮怎么回应与这句归谁无关 |
| 缺口账本 | 记一笔 `rout: "explicit"` + 被点名的专家，便于回看 |

不受 400 字闸限制：这里是确定性匹配，长派单书一样认得出。

反例（都仍然按原逻辑走）：`帮我把接口补上，前端也要改`（只是提到领域）、`作为一个审查专家，我觉得还行`（在引用别人的话，不是指派）、点到目录里没有的 id。

「你是X」要再看一眼紧邻的字（v0.20.18）：

| 句子 | 判定 | 为什么 |
|---|---|---|
| `你是后端工程师，帮我把接口补上` | 指派 | 逗号后面接的是活 |
| `你是后端工程师。项目目录 C:/w` | 指派 | 句号后面是任务 |
| `你是后端工程师吧，帮我看下这个接口为什么 500` | **不指派** | 那是在确认身份，实质是提问 |
| `你是后端工程师？` | **不指派** | 同上 |
| `我记得你说你是后端工程师` | **不指派** | 引用别人的话 |

判错的代价不对称：把提问误判成指派，这个专家连 role 都拿不到（`explicit` 不注入角色），比多注一段提示贵。所以只在「像派单书开头」的位置认。

### 决策回复不是闲聊（v0.20.19）

`可以按你推荐。`「继续」「好」在**没接单**的时候确实不该打扰——那是闲聊，插件闭嘴是对的。
但在**已经接了单**的项目里，这些话是对上一个问题的回答，是这一步往下走的依据。

真实 `runs.jsonl` 197 行里 166 行一条注入都没有，被吞掉的就是这类句子。沉默的代价不在这一句，
在下一步：模型收不到「这是回答，不是新需求」，就只能自己猜要不要重开一轮需求。

所以项目模式下「像不像一件活」不再是静默闸，而是**换个说法**：

| 这句话 | 项目模式下拿到什么 |
|---|---|
| 像一件活但没落到专家（`给导出加一个按日期筛选的功能`） | 「没命中具体专家」，提示按卡继续或这块该补人 |
| 不像活（`可以按你推荐。`） | 「**这句不像新活**」：这是对上一个问题的回答或一个决定，顺着刚才那件事往下走，别当成新需求重开一轮 |
| 已经点了人（派单书） | 什么都不给（v0.20.17） |

不像活的那条**刻意不提补专家**——它没活可派，提了只会诱导模型造一个任务出来。

克制没有丢：没接单（`idle`）时闲聊照样静默，`test/gap.mjs` 场景十四把这两套判据分开断言。

判「像不像活」用的是词表，词表跟着语言走。v0.20.20 补了两类它原来接不住的句子：

| 说法 | 原来 | 现在 |
|---|---|---|
| `把这批数据导一下` | 不像活 | 像活（`把` 字句几乎一定是在要求改动） |
| `把任务卡 #3 做完` | 不像活 | 像活 |
| `add a delete button to the list` | 不像活（中文词表对英文一律 false） | 像活 |

英文只收动词原形、不收名词，且带尾空格——`latest` 里有 `test`、`prefix` 里有 `fix`，
不带空格会把名词也收进来，那等于不判。

### 只对「人说的那一句」判（v0.19.0）

子代理的第一条 `user` 消息不是人写的，是父代理写的任务书——常常上千字，还带编号步骤。它同样是 `source.kind === "user"`，`lastUserPrompt()` 分不出来，于是被判了。

实测代价：一句「帮我做个员工报销审批的小工具」，在子代理会话里被记成 `rout:"hit", expert:"docs", cands:["docs"], secondary:"review"`——被点名的其实是任务书全文，提示跟需求毫无关系（模型照着检查点仍然走对了 intake，但注入的「主次」是错的）。

所以加一道长度闸：**超过 400 字的用户消息只注入检查点，不做点名**。一句话的需求到不了 400 字；粘一长段文档进来时同样不点名——长文的词面密度必然高，判谁都是运气。

检查点不受这道闸影响：它管的是「这一轮怎么回应」，与「这句归谁」无关。

### 长任务里不能只活第一步（v0.19.0）

插件挂的是 `agent/pre-step`，每一步都会进——**但每一步不一定还能看到「人话」**。

`lastUserPrompt()` 从后往前找 `source.kind === "user"` 的消息。一次连续作业（比如模型接了一句需求后自己跑 139 步）里，宿主交给 pre-step 的 `messages` 未必还带着那条消息，函数返回 `undefined`，代码在这里直接返回：

```js
if (prompt === undefined) return decision;
```

结果就是：**第 2 步起，插件整场下班。** 实测代价（[对照实验](./EXPERIMENT-2026-11-02.md)）：子代理跑 50 分钟 139 步，`runs.jsonl` 只写了 1 行，状态卡一次没注入，路由信号全集中在头两分钟。真实用例里也是同一个形状——61 分钟只有 7 条记录（= 7 个真人轮次）。

两处修法：

**① `lastPromptByAgent`**——按 `agentId` 记住最后一次见到的人话，找不到就复用。它仍然是那一轮的 `promptId`，所以检查点、缺口提示的去重逻辑一字不用改。

**② `shouldInjectState()`**——状态卡原来按「一条消息注入一次」去重，在长任务里等于「整场一次」。现在改成：**阶段一变立刻再说一遍**（这是真信息），否则每 `STATE_EVERY = 10` 步补一次。配套 `stepCounts` / `stateMarks` 两张表，超过 `MEMO_LIMIT = 500` 个 agent 就整表清空——清空最坏的结果是「同一句话再补说一次」，没有正确性问题。

为什么是 10 步：一个任务跑上百步时，每步贴一遍是在烧上下文；完全不贴，模型第 60 步就会忘了自己在 `build`。阶段变化优先于步数——那才是真信号。

### 接单专家有「做个」这类触发词，但会**让位**

> v0.18.0 改。上一版不给 `intake` 这类词，理由见下；这个做法在真实用例里失效了。

给 `intake` `做个 / 开发 / 搭建` 的风险是真的：它会变成万能兜底，把「帮我做个报价单」「给我做个登录页」全抢走（b 集实测过 `帮我做个报价单` 从 `data` 变成 `intake`）。

但不给词的代价更大：真实首句「我想做一款Windows记账软件」**一个触发词都不沾**，落空且静默，整场 0 次 `expert()`。

所以改成结构上解决，而不是靠词表回避：**`kind: intake` 的专家在有别的专家过线时自动让位**（`lib/router.js` 的 `hasRival` / `demoted` 排序键）。

- 有 rival 过线 → `intake` 排到所有 rival 之后，且**不参与** `ambiguous` / `multi` / 主次的判定；
- 没有 rival 过线 → `intake` 正常赢，全新项目从它进门。

回归验证：a/b/c 三集仍 20/20、20/20、8/8，`帮我做个报价单` 仍然归 `data`，「把这个需求文档改成给老板看的版本」从错判 `intake`(4.0) 改回 `docs`(3.5)。

落空时的第一句也改了：**有接单专家就先接单**，不再先说「没有干这个的人」——全新项目几乎必然落空，先说没人等于把最常见的场景说错。

```text
【能力路由 · 没命中具体专家】
这句话没有直接落到某位专家的触发词上，但**不等于没人接**：先 `expert("intake")` 接单，
让它把模糊需求收敛成 `REQUIREMENTS.md` + `TASKS.md`，再按任务卡分派给领域专家。
拆完如果确实有没人接的部分，再对用户说「这块我手上没有对应的人」…
```

也就是说：**intake 是入口，不是竞争者**——它靠「让位」规则保证不抢活，而不是靠削弱自己的能力。

### v2 入口：专家目录 + `expert(name)`（`catalog` / `expertTool`，默认开）

规则匹配（本节上半）是 v1 的做法：插件替模型选人，选错就没救。v2 把判断权换了个位置：

| 产物 | 放哪 | 为什么 |
|---|---|---|
| 专家目录（`catalogText()`） | 系统提示 `capability-experts`，order = 配置 `order` + 1 | 内容稳定 → prefix cache 能命中；每步会变的只有状态卡 |
| `expert(name)` 工具 | `ctx.tools.register()` | 详情（`role.md` 全文 + 交付物 + 交接）按需取，不常驻上下文 |

目录长这样（渲染自十个专家包，`kind` / 必装技能 / 产出 / 交接全部就位）：

```text
## 可用专家（能力路由）
- **后端工程师**（backend，worker）：接口、数据模型、并发与服务边界
  主力技能：codebase-design、domain-modeling
  备用技能：research
  产出：接口定义、数据模型、迁移脚本
  常交给：frontend、review
- **接单专家**【入口】（intake，intake）：…
- **审查专家**【收口】（review，reviewer）：…
- **调研专家**【调研】（research，scout）：查市面上有没有现成方案，避免重复造轮子
  主力技能：research
  产出：PRIOR-ART.md
  常交给：intake、backend、frontend
```

三种角色标签在名字后面标出来：目录里十个人看起来一样平，不标的话模型会随手挑一个开工，而入口、收口、调研的位置其实都有讲究（v0.20.0 补了【调研】）。

**不用 `defineTool` 的原因**：它是宿主包 `@deepseek-ai/dsh-tools` 里的函数。本插件零依赖、装在用户目录里，不该反过来解析宿主的依赖树——那会在宿主升级时静默炸掉。所以直接给 `register()` 需要的形状：

```js
{ name, description, parameters /* 标准 JSON Schema */, output: { schema, render }, execute }
```

已核对 `dsh-tools` 的 `register()`（`lib/index.js:2974`）：它只校验 `output.render` 是函数、`output.schema` 落在支持的 JSON Schema 子集内，`parameters` 原样透传给模型。`required` 用标准数组写法（宿主 `defineTool` 的 spec 写法是另一套，这里用不到）。

- `catalog: false` 不注入目录；`expertTool: false` 不注册工具；没有专家包时两者都不注册（不往系统提示里塞空段）
- 与检查点的关系是**会抢注意力**：目录说「按阶段换人」，检查点说「有黑洞问一句」。项目模式下检查点要降级为一句——这是第 4 步的活，现在两条都还在。

## 六、角色注入（`role`）

命中专家后，把该专家的 `role.md` 作为一条 user 消息追加：

```js
{
  role: "user",
  id: randomUUID(),
  content: [{ type: "text", text: "【能力路由 · 当前专家：前端工程师】\n\n# 角色：前端工程师…" }],
  source: { kind: "capability-router-role", form: "notice", forPrompt: <用户消息 id>, expert: "frontend" }
}
```

- 一条用户消息只注入一次（独立账本 `rolePrompts`）。
- 没命中、缺 `role.md`、或 `experts: false` 时不注入。
- **实机验证过**：2026-11-01 在 DSH Desktop 0.2.1 上收到过完整的 `frontend` 角色消息。

和检查点的区别：检查点说的是「怎么处理这句话」，角色说的是「你是谁、按什么标准交活」。两者可以同时出现，顺序是**角色在前、检查点在后**。

## 七、缺口提示（`gap`）

匹配落空时说一句，分三种（v0.18.0 起多了一个「主次」）：

**分不清**（`ambiguous`）——不硬选，问一句：

```text
【能力路由 · 分不清】
这句话同时落在「前端工程师」和「排障工程师」的地盘上，两边都说得通。
别硬选：先问用户一句「更偏 前端工程师 还是 排障工程师？」，给 2~3 个具体选项，一次问完。
用户点完再开工——选错的代价不是改代码，是整段活白做；但也别为了省这一问，两边各做一半。
```

**没人接**（`miss`，且这句话像在派活）——有接单专家就先接单：

```text
【能力路由 · 没命中具体专家】
这句话没有直接落到某位专家的触发词上，但**不等于没人接**：先 `expert("intake")` 接单，
让它把模糊需求收敛成 `REQUIREMENTS.md` + `TASKS.md`，再按任务卡分派给领域专家。
拆完如果确实有没人接的部分，再对用户说「这块我手上没有对应的人」…
```

项目模式下（`phase !== "idle"`）文案换一支：单已经接了，不再劝 `expert("intake")`，改成「按卡继续，还是这块该补人」。原文见第九节「缺口提示与记账」。

一个专家包都没有时，才退回旧文案（列出已有专家 + 怎么说缺人 + 怎么造包）。

**主次**（`hit` 但带 `secondary`）——头名明确，副的那部分也得有人管：

```text
【能力路由 · 主次】
主要是「数据与办公」（文档与写作 那边也占了一部分）。
按主领域开工，但**交付前把 文档与写作 那部分一起处理掉**——别只交一半。
需要两份产出就分两次 `expert()`，别自己硬扛另一边的活。
```

判据是「次名 ≥ 1.5 倍阈值，且命中词不被头名的词面包含」——「数据」落在「数据库」里只是噪音，不算副领域。

### 「像不像一件活」

`miss` 不设防地说话会变成噪音——「今天中午吃什么」也匹配不到专家。所以加了一道闸（`lib/gap.js` 的 `looksLikeTask`）：出现任务形态的词才开口（帮我、做个、改成、排查、怎么、能不能……）。

宁可漏报：漏报的代价是少一句提示，误报的代价是每句闲聊都被插一段废话。

实测 10 句日常说法，触发 5/10：派活的 4 句开口，闲聊 3 句静默，另外 3 句直接命中专家。

`ambiguous` 不设这道闸：分不清本身就是信号，而且此时两边都说得通，说清哪两个在抢比让模型自己蒙一个更有用。

去重与 `hint` 共用同一套账本机制。

---

### 跨领域（`multi`）也有话说

```text
【能力路由 · 跨领域】
主：后端工程师（5）；副：前端工程师(3.5)、文档与写作(2)。
按主领域开工，但**交付时把副的那部分一起交**——别只做一半，也别自己一个领域一个领域串着硬扛。
如果是新项目（不是改既有东西），先 `expert("intake")` 拆任务卡，再按卡分派。
两边分量接近（分差 < 0.5）时，先问用户一句哪边更急，问完再动手。
```

这也是「匹配器降级为提示」的落点：`multi` 不该由插件替模型拆活，它只负责指出「这里不止一个领域」。

## 八、专家包 v2 与技能供给体检

### v2 字段

`expert.yml` 在 v1 之上加了三个元数据，并把 `skills` 从「名字数组」升级成「依赖声明」：

| 字段 | 取值 | 作用 |
|---|---|---|
| `kind` | `intake` / `worker` / `reviewer` / `scout` | 名字决定行为：接单的先出文档，审查的按验收标准收口，调研的先查市面有没有现成的。缺省 `worker`；写错只告警、按 `worker` 处理。`scout` 是 v0.20.0 加的，理由见第九节「`scout`：调研专家怎么进流程」 |
| `handoff` | 专家 id 列表 | 我通常把活交给谁，只作提示，不强制 |
| `deliverables` | 文件名列表 | 我该产出什么，审查专家按同一份清单验收 |
| `skills` | 依赖声明列表 | 每项 `{name, required, source}`，见下 |

写法（YAML 子集只支持一层流式映射，所以一条依赖写一行）：

```yaml
kind: worker
handoff: [frontend, review]
deliverables: [接口定义, 数据模型]
skills:
  - {name: codebase-design, required: true, source: local}
  - {name: writing-plans, required: false, source: host}
```

`source` 的三种取值，决定体检怎么对待它：

| source | 含义 | doctor 怎么处理 |
|---|---|---|
| `host` | 跟着 DSH 一起装的（office / pdf / playwright 这类） | **不查**：用户目录里没有，但一定存在，查了就是假红 |
| `local` | 装在 `~/.dsh/skills/<name>/SKILL.md` | 逐个数，缺了报红 |
| `unknown` | 老写法 `skills: [pdf]` 的默认值 | 按缺失报出来，逼着标注来源 |

老包不用改：`skills: [a, b]` 仍然能读，等价于「两项、非必装、来源不明」。

### 技能供给体检：`npm run doctor`

```text
$ npm run doctor
技能供给检查：专家 10 个，已装技能 29 个

backend  后端工程师（worker）
  ✓ codebase-design                    必装  local
  ✓ domain-modeling                    必装  local
  ✓ test-driven-development            必装  宿主自带
  ✓ research                           可选  local
  常交给：frontend、review
  该产出：接口定义、数据模型、迁移脚本
...
必装技能都有着落。
```

- `--json` 给机器读；`--dir <绝对路径>` 额外扫一个技能目录（默认只扫 `<DSH_HOME>/skills`）
- **退出码**：0 必装齐全；1 有必装缺席；2 参数错
- 同一个技能被多个专家声明为必装、又都没装时，只报一次

### 这条命令明确不做什么

- **不装技能、不打包技能**。技能源码永不进本插件——别人的技能一直在更新，内置就吃不到新特性。装由用户或 Agent 自己的技能管理负责。
- **不查版本**。宿主的技能目录不带版本号，查了也只能编。
- **不阻断加载**。专家包声明了没装的技能，插件照常工作，只是这个专家的角色提示词会少一块实际能力——所以体检要能随时跑，而不是挂在安装流程里。

## 九、项目模式：会话状态、阶段闸门、`runs.jsonl`

一个会话一旦「真开工」，三条协议会互相抢注意力：系统提示里的专家目录说「按阶段换人」、当轮检查点说「有黑洞问一句」、规则匹配器说「我替你选好了前端」。项目模式做的就是**让这三条只剩一条在说话**。

### 阶段从哪来：只读事实，不猜

| 动作 | 阶段变化 |
|---|---|
| 打开接单专家（`expert("intake")`，`kind: intake`） | `idle` → `spec` |
| 打开实现类专家（`kind: worker`） | 不变（只记进「在场专家」） |
| 打开调研专家（`kind: scout`） | 不变（只记进「在场专家」；闸门给的是「先出 `PRIOR-ART.md`」，不是「先别开工」） |
| `expert(id, { phase: "build" })` | 显式推进到实现（`spec → build`） |
| `expert(id, { phase: "review" })` | 显式推进到审查（`build → review`） |
| `expert(id, { phase: "deliver" })` | 显式推进到交付（`review → deliver`）；**到此为止**，`advancePhase` 不后退，要重做只能另建项目目录 |
| `build` 阶段打开审查专家（`kind: reviewer`） | `build` → `review` |

状态落在**项目**里：`<项目目录>/.capability-router/state.json`。会话文件 `<STATE_DIR>/sessions/<sessionId>.json` 只留一个指针（外加阶段镜像），pre-step 先看项目状态、再回落会话自己。

为什么要按项目而不是按会话：多代理协作时同一个项目会被好几个会话接手——接单一个、实现一个、审查一个。验收里真出现过同一个项目在三个会话里分别是 `spec` / `idle` / `review`，谁也说不清现在到哪一步了。**阶段属于项目，会话只是执行者。**

**`project` 参数怎么处理（v0.20.5）**：接受绝对路径和相对路径。相对路径按**宿主进程的 cwd** 解析后落盘，并在 note 里回显解析后的绝对路径——宿主的 cwd 与会话的工作目录不是一回事，不回显就只能靠猜。状态文件里存的永远是绝对路径，换个 cwd 也找得回来。

写盘失败会说话：`writeState()` 返回 `{ state, error }`，`expert()` 把 `error` 拼进 note（「⚠️ 状态没能落盘（ENOTDIR）：…这一轮的推进只在本轮有效，下一轮会退回旧状态」）。以前这里 `catch {}` 完就当没发生，理由是「状态卡是提示，不是账本」——但 `project` 指到一个**文件**上时，状态每轮都丢、每轮都从头开始，而模型看到的 `found:true` 一切正常。**静默失败比不记更贵，因为它让人以为记下了。**

会话 id 取 `payload.agent.id`（等于 `agent.session.id`，`dsh-agent/lib/index.js:513-514` 有断言）。项目路径由 `expert(name, { project: "<绝对路径>" })` 显式给出，之后这个会话的后续调用会自动沿用记住的路径。文件坏了、丢了、字段怪，都当作「空闲」，不让状态机把挂载搞崩。

### 为什么需要「显式交卷」

`spec → build` 这一步没有谁能替模型判断：需求确认完没完，取决于 `REQUIREMENTS.md` 写没写好、用户认不认，而插件拿不到会话的工作目录（`agent.session` 上没有 workspace 字段），没法靠文件是否存在来推断。

所以给它一个显式出口：**交卷时说一声**。

```text
expert("intake", { phase: "build" })    // 需求文档交付，进实现
expert("review", { phase: "review" })   // 实现完成，进审查
expert("review", { phase: "deliver" })  // 审查通过，进交付
```

`advancePhase()` 只允许**往前走**（可以一次跨多格，往后一律拒绝），被拒时把原因写进 `note`，并带上 `⚠️` 前缀：

```text
⚠️ 阶段没有推进：阶段只能往前走：当前 review，目标是 spec
```

允许跨格是验收逼出来的：多代理协作时新会话从 `idle` 起步，它接手的是已经在 `build` 的项目——不允许跨格，阶段就没法对齐。禁止后退这条保留，因为它挡的是「手滑把项目打回原形」。

没有这个出口，会话会永远卡在 `spec`，状态卡会一直念「去做需求文档」。

### 五个阶段各说一句话

> v0.18.0 增加了 `deliver`：原来阶段止于 `review`，「审完了」和「交出去了」是同一格——
> 「审过了才说完成」和「根本没审也说完成」在状态上长得一模一样。真实用例里成品用户打不开、
> README 写错原因，就是这一格缺位的代价。

| 阶段 | 状态卡里的「下一步」 |
|---|---|
| `idle` | 普通对话；确认要开工后打开接单专家（`expert("intake")`） |
| `spec` | 先出 PRIOR-ART.md，再收敛 `REQUIREMENTS.md` + `TASKS.md`，然后交给实现的专家 |
| `build` | 按任务卡推进；收口前交给审查专家 |
| `review` | 按同一份验收标准逐条核对，通过才算完 |
| `deliver` | 交付核对：真的装得上、真的开得起来、README 写的是真原因；核对完再说「可以用了」 |

### 闸门是提示，不是拦截

宿主没有工具级拦截钩子，所以闸门只在 `expert()` 的返回里追加一句 `note`：

- `spec` 阶段打开 worker → 「需求还没确认（`REQUIREMENTS.md` 与 `TASKS.md` 未产出），先别开工」
- `idle` 阶段打开 reviewer → 「还没有可审的东西」
- `idle` 阶段打开 worker → 「还没接单。先 `expert("intake")`…」（v0.18.0 补：跳过接单是最容易犯的错，整场 0 次 `expert("intake")` 就是这么来的）
- `review` 阶段打开 worker → 「正在审查，只核对不改代码」
- `deliver` 阶段打开 intake → 「已经交付了，不用重新接单」

### 缺口提示与记账（v0.20.1 修 L1）

v0.20.0 把「提示」和「记账」绑在同一个条件上（`!projectMode`），代价是**接单之后 `gaps.jsonl` 整段断流**——实测整个会话零记录，最后一条停在 phase 推进到 `spec` 的那一刻。面板和 `tools/gaps.mjs` 只看得见 `idle` 的语料，等于越到真正需要补人的阶段越没数据。v0.20.1 拆开：

| 集合 | 管什么 | 去重语义 |
|---|---|---|
| `gapLogged` | 记账（`gapLog`） | **一句一次**，不管这句最后说没说出口——账本与提示策略无关 |
| `gapPrompts` | 注入（`gap`） | **一句一次**；被状态卡压住的那一轮**不标记**，下一步补说 |

所以项目模式下的顺序是：状态卡优先，这一轮缺口提示让位；下一轮没有状态卡了，缺口提示补上来。落空不再静默，也不会和状态卡同时喊话。

`miss` 的文案按模式分岔（`gapText(verdict, catalog, text, { phase, phaseLabel })`）。项目模式里不再劝接单——单已经接了，再劝一次是错的：

```text
【能力路由 · 没命中具体专家】
这句没落到某位专家的触发词上；项目已在「实现」阶段。
先自己判断：按任务卡继续做，还是这块确实该补一个专家——别硬派给沾边的，派错了它会把错的 role.md 注进上下文。
```

`idle` 时仍是原来那句（先 `expert("intake")` 接单）。`hit` / `multi` / `ambiguous` 三个分支**逐字未动**。

记账行多了一个**可选**字段：有阶段时写 `"phase"`，没有就不加这个键（旧行格式不变，读的人不必处理「存在但为 null」）。`tools/gaps.mjs` 的聚合 key 还是「结论 + 原话」，只是每条后面多带一段 `阶段 spec/build`——同一句话在 `idle` 落空和在 `build` 落空是两种信号。

面板的缺口页（`lib/panel.js` 的 `readGaps`）只按原话聚合、不读 `phase`——同一句在两个阶段各落空一次会并成 `×2`，看不出阶段差。面板缺口队列自 v0.20.12 起也带「阶段」列（聚合时保留 `phases`，去重保序；v0.20.1 之前的老行没有 `phase`，显示 `-`）。命令行想看全量用 `tools/gaps.mjs`。

### 用户水平（`level`，v0.20.0）

**怎么判**：接单第一问——「这件事你想让我一步步讲清楚，还是直接给结论？」问完落 `expert("intake", { level: "novice" })` 或 `"pro"`。老手不解释术语、直接给取舍；新手每个术语第一次出现时用一句人话解释，命令写全。

**存哪**：进项目状态文件 `<项目>/.capability-router/state.json`，会话文件留一份镜像。`normalizeState()` 只认 `"novice"` / `"pro"` 两个字符串，别的值当没写——**未判定就是整个键不存在**。写成 `level: undefined` 跟没写等价：`JSON.stringify` 会把这个键整个丢掉。

**影响什么**：

| 落点 | 判定后 | 未判定时 |
|---|---|---|
| 状态卡 | 多一项「用户水平：新手 / 老手」 | 多一项「用户水平：未判定」 |
| `spec` 阶段打开 worker 的闸门 | 只有「需求还没确认，先别开工」 | 后面多一句「先问一句用户想听多细（新手要细节，老手直接上）」——判定后这句不再出现 |
| 打开任何专家的 note 末尾（v0.20.3） | 「用户水平：新手——先解释术语和为什么，再给命令；别默认它知道技术栈和工具名。」/「老手——直接给结论和命令，省掉背景铺垫。」 | 不追加 |
| 专家 `role.md` | 不受影响 | 不受影响 |

最后一行是这一版的硬边界：**`level` 只改提示文案，不改专家行为定义**。`role.md` 是静态文件，同一个专家对新手和老手说的是同一段话。

v0.20.3 补的是第三行。在此之前 `level` 只有 `experts/intake/role.md` 自己读——接单专家问了「想听细节还是直接上」，然后把答案写进项目状态，接着开 `backend`，而 `backend` 的 `role.md` 是静态的，压根不知道有人回答过这个问题。现在 `expert()` 每次返回的 note 末尾都带一句水平提示，九位干活专家都能看见。

**为什么不去改那十份 `role.md`**：按 level 改写角色提示词等于给每个 level 各养一套缓存键，每次换 level 就是一次全价冷启动。**能放进「每步都变的那一层」的，就别放进「只有开会话才变的那一层」。** 代价是水平只影响「怎么说」，不影响「先做什么」——真正的新手模式应该连步骤拆法都不一样，那要动角色提示词本身（见 [TASKS.md](../TASKS.md) 遗留项 L3 的升级路径）。

### 项目模式下的检查点：只留「这句是提问」（v0.20.9）

项目模式一开，三分法检查点整体让位给状态卡。但状态卡讲的是「这个阶段该干什么」，不问「用户这句话是什么」——实测提问、命令、征询三种句子拿到的注入一字不差。

所以留了一个窄口：`looksLikeQuestion(text)` 为真时，补一条 `【能力路由 · 这句是提问】`（45 字）。任务句仍然只有状态卡，撕注意力的问题只出现在本来就该干活的那一半。

同一个窄口还留了第二条：**副领域提示**（`【能力路由 · 主次】`）在项目模式下照常出现。任务卡是**事先**分好的工，而用户临时插进来的跨领域请求不在卡上——实测「登录页的样式全乱了，顺便把接口也改一下」原来只拿到状态卡，模型照着「按任务卡推进」只会做掉卡上那一半。

被关掉的那一条只有接单提示：「接单不是终点」在项目模式里是废话，因为项目模式本身就意味着已经接过单。

**一条消息只说一句话（v0.20.16）。** 提问轮会顶掉同轮的状态卡、缺口提示和主次提示——它们分别说「按任务卡推进」「按主领域开工」「别顺手改代码」，叠在一起是互相作废。让位是**一轮**：提问不调 `shouldInjectState`，因此不写 `stateMarks`，下一句不是提问时状态卡照常出现。缺口**记账不受影响**——账本记的是「这句没落到谁头上」，跟它最后说了什么无关。

**v0.20.15 补了一个漏洞：委婉请求。** 第一版判据是「有疑问形态**且**没有派活动词」，于是「能不能把这个按钮改大一点」「这个可以做成深色主题吗」「界面配色能不能再淡一点」全被判成提问——而它们要的是改动。注入劝它「别顺手改代码」，该干的活就停在那儿。现在多一道排除：`CHANGE_HINTS`（处置式的「把」、改变动作「做成/调成/变」、程度补语「一点/大点/淡点」）。有要变的量，就是活。

判错的代价不对称，所以排除宁可宽：把命令判成提问，会让活停下；把提问判成命令，只是少一句提醒。反过来的「能不能离线用」「这个功能支持多语言吗」问的是能力与支持，仍是提问。

`looksLikeQuestion` 与 `looksLikeTask` 是两个问题，不能互相顶替：后者把「怎么 / 如何 / 为什么」算成活（对缺口提示是对的），前者要求「有疑问形态**且**没有派活动词」——「导出为什么失败？帮我修一下」两个特征都有，那是活。

### 阶段推进时的产物核对（v0.20.8）

`expert()` 把阶段推进到「实现」的那一刻，会看一眼项目目录里有没有 `REQUIREMENTS.md` 和 `TASKS.md`，缺哪份就在 `note` 里点名。

**为什么放在这里**：状态是插件记的，文档是模型自己写的，两边互不校验。插件说「按任务卡推进」的时候并不知道卡在哪；模型写卡的时候不受任何约束。`expert()` 是唯一同时握着**项目绝对路径**、**推进前阶段**、**推进后阶段**三样东西的地方——错过这个点，再想核对就只能事后审计了。

**两个刻意的退让**：只提示不拦（文件名可以自定义，插件没有资格判定「你没有需求文档」）；带撤回口（「如果你们用了别的文件名，忽略这句」）。只在阶段**真的变了**时说一次，重复调 `expert("intake", { phase: "build" })` 不再提。

### 方案确认（`approved`，v0.20.0）

**默认 `false`**，表示「方案还没被用户点头」。

| 触发 | 结果 |
|---|---|
| `expert("intake", { phase: "build" })`（阶段真的往前走了） | **不改 `approved`**（v0.20.2 起）。未确认时返回一句提醒：「阶段已推进到实现，但方案还没记为确认」 |
| `expert(id, { approved: true })` | 显式确认——**唯一的置真路径** |
| `expert(id, { approved: false })` | 撤销 |

**边界在哪**：它是软提示。`approved: false` 不拦任何动作，只让状态卡多一句「方案：待确认」。理由是用户说「直接做」是最常见的确认方式，硬拦等于用流程惩罚一个已经想清楚的人（决策记录见 [DESIGN.md](../DESIGN.md) 第十六节第 1 条，及其 v0.20.2 修正）。

### 重开（`reopen`，v0.20.14）

`advancePhase()` 从来只许往前，`deliver` 是终点：进得去、出不来。这条规矩是对的——**阶段是闸门的主语**，`gateNote` 每一句都由 phase 决定，phase 能随手改就等于闸门能被模型自己绕过。代价是「交付之后想回头改」只能另建项目目录，项目文件、任务卡、验收记录全断在半路。

折中是留一个**必须说出口、且会留痕**的入口：

| 触发 | 结果 |
|---|---|
| `expert(id, { project, reopen: true })` 且当前 `deliver` | 阶段退回 `build`，状态里记 `reopenedAt`，note 说「已重开……这次的改动不在上一轮的验收范围里」 |
| `reopen: true` 但不在 `deliver` | 阶段不动，note 明说「reopen 只对已交付的项目有效：当前在「实现」阶段，没有重开」 |
| 重开后再传 `phase: "spec"` | 照旧被 `advancePhase` 拒绝：「阶段只能往前走」——`reopen` 是唯一一次后退，不是万能回退键 |

状态卡完整版多一段「｜重开于 11-02」（超长的短版不带它：重开是当场就知道的事，状态卡只负责让后来的人看见「退过」）。

只认严格布尔：`"true"`、`1` 都不算确认。状态文件是外部输入，宽容解析在这里只会制造假阳性。

### 状态卡长什么样（v0.20.0 的四态）

一步一行，四种情况（原样抄自 `stateCardText()` 的输出）：

```text
【能力路由 · 项目模式】阶段：需求确认（spec）｜方案：待确认｜用户水平：未判定｜在场专家：intake｜下一步：先出 PRIOR-ART.md，再收敛 REQUIREMENTS.md + TASKS.md，然后交给实现的专家
【能力路由 · 项目模式】阶段：需求确认（spec）｜方案：待确认｜用户水平：新手｜在场专家：intake｜下一步：先出 PRIOR-ART.md，再收敛 REQUIREMENTS.md + TASKS.md，然后交给实现的专家
【能力路由 · 项目模式】阶段：实现（build）｜用户水平：老手｜在场专家：intake、backend、qa｜下一步：按任务卡推进；收口前交给审查专家
【能力路由 · 项目模式】阶段：空闲（idle）｜方案：待确认｜用户水平：未判定｜在场专家：无｜下一步：普通对话；确认要开工后打开接单专家（`expert("intake")`）
```

三条要看清的结构差异：

1. **已确认时整段「方案」不出现**（第三行）——已确认是常态，不值得占字；只有「待确认」值得提醒。
2. **总长超 120 字先砍「在场专家」**（第一、二行带头，砍了就是 `…用户水平：新手｜下一步：…`）。那一项最不影响下一步动作。
3. **`idle` 是真实状态**，不是缺省兜底：还没接单时就这样，`下一步` 明说该干什么。

### `scout`：调研专家怎么进流程

调研必须在 `spec` 阶段做——它是写需求的输入。但 `spec` 阶段的 `worker` 闸门说的是「先别开工」，两句话直接打架。

解法是给调研一个自己的 `kind`：`scout`。

- `gateNote()` 里 `scout` 分支**排在所有 worker 分支之前**（`lib/state.js:228`），返回的是「先出 `PRIOR-ART.md`（谁能直接用 / 谁能改着用 / 都不行为什么），再决定需求怎么写；没查过现成的就动手，等于重造一遍。」
- 顺序是硬约束：写反了，`spec` 阶段打开调研专家会说「先别开工」，等于让调研专家在自己的工作阶段违反闸门，自相矛盾。
- 目录里标【调研】（`lib/catalog.js:24`），模型一眼看得出它不是普通 worker。
- 目前只有 `research` 一位是 `scout`。新造 scout 专家要同时在 `lib/experts.js:131` 的 `KINDS` 里有这个取值，否则会被降级成 `worker` 并告警。

### `/api/state` 与 `readSessions()`：`null` 不是省略

面板那条数据通道（`lib/panel.js:59-67`）对两个新字段的处理，和状态文件**故意不一样**：

| 字段 | 状态文件里的样子 | `/api/state` 里的样子 |
|---|---|---|
| `approved` | 恒为布尔，缺省 `false` | 恒为布尔 |
| `level` | 未判定时**没有这个键** | 未判定时 `null` |

为什么不在接口层也省略：`JSON.stringify` 会把值为 `undefined` 的键整个丢掉。省略之后 client 拿到的对象里根本没这个键，就分不清「用户还没判定」和「这是老版本的状态文件、压根没有这个字段」。`null` 把两种情况分开。

老记录照常能读：老 `state.json` 没有这两个键，读出来就是 `approved: false` / `level: null`，不会让整条记录读失败（`test/web.mjs` 场景八「老记录补字段」）。

### 项目模式下自动降级的四个东西

| 东西 | 项目模式下的行为 | 原因 |
|---|---|---|
| 当轮检查点（`hint`） | **不注入**，换成一行状态卡 | 状态卡已经说了该干什么，两条协议同时喊话会撕注意力 |
| 缺口提示（`gap`） | **和状态卡互斥**：状态卡说话的那一轮不注入，顺延到下一步 | 两条协议同时喊话会撕注意力；但落空本身不能让模型瞎着，所以只是排队，不是取消（v0.20.1 修 L1） |
| 缺口记账（`gapLog`） | **照常记**，一句一次 | 记账和「说不说」是两件事。v0.20.0 把两者绑在同一个 `!projectMode` 条件下，结果接单后 `gaps.jsonl` 整段断流 |
| 规则角色注入（`role`） | 只要 `catalog` 开着就**不注入** | 目录已经把选人交回模型，再注入一份 `role.md` 是在唱反调（真机上观察到过：子代理在做「检查系统提示」，却收到【当前专家：后端工程师】） |

最后一条是**默认行为**，不是项目模式专属：目录（v2）在场时，v1 的规则角色注入整体退场。上面两条（缺口提示 / 记账）是 v0.20.1 才拆开的——它们原来绑在同一个条件上，一起被关掉。

### `runs.jsonl`

每步一行，用来回答「它刚才为什么这么干」：

```json
{"at":"2026-11-01T12:20:31.004Z","session":"b8aa5600-…","phase":"spec","promptId":"…","rout":"miss","expert":null,"task":true,"cands":["backend","data"],"secondary":null,"injected":["capability-router-state"]}
```

只记判断，**不记原话**——原话在 `gaps.jsonl`，两件事分开看。64 KB 截断，与其它账本一致。

**v0.20.3：一份数据，两种粒度。** 面板的「最近 25 步」原来是 `runs.slice(-25)`——直接截行。真实会话里一句长任务能跑 55 步（实测 `session-413de83f` 的 111 条 run 只对应 4 个 promptId，单句最多 55 步），截 25 行等于那张表只看得见同一句话的一小段，别的什么也看不见。

现在面板先 `foldRuns(rows)` 再截：按 `promptId` 把**连续相邻**的同句合并成一行，`steps` 计数、`at`/`phase`/`rout`/`expert` 取最后一步、`injected` 取并集；每行路由列尾挂 `×55`。读取上限也同步从 200 行提到 2000——200 行在每步一行的粒度下只够两三句。

两个刻意的限制：**只合并相邻的**（不同会话交错写进同一文件时，跨行合并会把别人那一步算进这一句）；**缺 `promptId` 的老记录不合并**（无键可归）。`readRuns()` 保持按行（`/capability-router/api/state` 自 v0.20.11 起给的是**折叠后**的形状：每句一行、带 `steps`、注入取并集、最近 200 句）不动——`tools/match.mjs` 的 a/b 判定按句算命中率，两边口径混了会把「命中 20 句」读成「命中 20 步」。

v0.18.0 补了三个字段，为的是事后能回答「当时为什么这么选」：`task`（这句像不像活）、`cands`（当时的候选）、`secondary`（副领域被谁接着）。真实用例复盘时，`rout:"miss"` 配上 `task:false` 才能看出「首句被判成闲聊」——不记这两个字段就只能看到 miss，看不出为什么没说话。

## 十、技能目录收窄（`narrow`，已删除）

> **v0.7.0 已删除**：`lib/narrow.js`、`test/narrow.mjs`、配置项 `narrow` 与 `alwaysVisible` 全部移除，本节的代码描述只作历史记录。为什么删：①它服务错了对象——技能目录服务整个会话，不服务单条消息的裁决；②代价明确（目录全量重发、每个被覆盖技能一条重名告警）；③真机上只对插件层生效（49 → 41，只收 8 个）。替代方案见 [ARCHITECTURE 第六节](./ARCHITECTURE.md#六收窄narrow-退役)。

### 想做什么

命中某专家后，把该专家用不到的技能设成 `modelInvocable: false`：模型看不见，用户仍可 `/name` 调用。

### 怎么做

宿主没有「排除技能」的接口，只能**冒名接管**：对每个要收的技能交一份同名候选，`rank: -1` 压过原 provider。排序规则是 `rank → providerOrder → localOrder`，同名的先到先得（`dsh-skill/lib/index.js:519-521`）。

三条守住的边界：

1. **不封锁**：`provider.get()` 把本 provider 的 `list()` 临时静音、让宿主重算目录，此时原 provider 胜出，拿到正文再返回。被收起的技能照常能 `/name` 加载。
2. **逃生口**：匹配落空立刻恢复完整目录，不需要用户记命令。
3. **少动目录**：记住当前专家，同一专家不重算。目录消息是全量替换的，每变一次 prefix cache 重算一次。

### 实机结论：只对插件层的技能生效

2026-11-01 真机跑了一遍（49 个技能，命中 `frontend` 后应该只剩 5 个）：**只收起 8 个**——插件自带的 `office ×7` 与 `diagnose-windows-sandbox-acl`；用户目录下 29 个技能纹丝不动。

原因在宿主的层语义：

- `registerProvider` 把 provider 注册进**调用方所在的作用域层**（`dsh-skill/lib/index.js:147-178`）；
- 读目录时按 `[global, ...scope chain]` 合并，**靠后的层覆盖同名条目**（`:298-310`）；
- 本插件挂在 profile 上，只能写全局层，因此压不过作用域层里的同名用户技能。

`rank: -1` 只在同一层内决定同名胜负，跨层无效。这不是参数没调好，是机制的天花板。

**所以它现在默认关闭，且只该被理解为「收插件带来的噪音技能」。** 要按专家收窄用户技能，需要宿主提供作用域挂载点或目录过滤钩子。

打开它有额外代价：每个被覆盖的技能一条 `ignored because a higher-priority skill already exists` 告警（只在目录缓存失效时出现），目录全量重发一次。

## 十一、缺口记账（`gapLog`）与汇总

每次「没人接」或「分不清」时，把原话记进 `<STATE_DIR>/gaps.jsonl`：

```json
{"at":"2026-11-01T10:01:00.000Z","kind":"miss","text":"帮我做视频监控系统","candidates":[]}
{"at":"2026-11-02T02:11:00.000Z","kind":"miss","text":"这个审批流谁管","candidates":[],"phase":"build"}
```

关键约束：**记账与「这句该不该有人接」用同一个判据**，与「这一轮要不要开口」无关。闲聊既不提示也不记账——否则记录里全是「今天中午吃什么」，没法用来决定造什么专家。

第二行的 `phase` 是**可选**字段（v0.20.1 起）：有阶段就写，`idle` 不写这个键。项目模式照常记账——v0.20.0 把记账和提示绑在同一个 `!projectMode` 条件下，接单之后 `gaps.jsonl` 整段断流。

汇总：

```bash
npm run gaps                 # 去重后按次数排序
node tools/gaps.mjs --all    # 全量
node tools/gaps.mjs --json   # 机读
```

```text
× 2  帮我做视频监控系统
      没人接  ·  最近 2026-11-01T10:01:00.000Z
× 1  帮我写一下这个接口的文档
      分不清/backend|docs  ·  最近 2026-11-01T10:03:00.000Z
× 1  这个审批流谁管
      没人接  ·  阶段 build  ·  最近 2026-11-02T02:11:00.000Z
```

同一句话出现三次，就是三次都没找到人接——那是「该造专家」的信号，不是「该改匹配」的信号。坏行会被跳过，不会让整份文件读不出来。

## 十二、造专家（`tools/forge.mjs`）

```bash
node tools/forge.mjs rtsp --name 流媒体工程师 \
  --description "摄像头接入、推流、回放与存储" \
  --triggers 摄像头,推流,RTSP,回放,目标检测 --skills pdf
```

| 参数 | 说明 |
|---|---|
| `<id>`（位置参数） | kebab-case，只允许 `a-z 0-9 -` |
| `--name` | 必填，专家名 |
| `--description` | 必填，一句话说明干什么、什么时候找它 |
| `--triggers` | 必填，逗号分隔 |
| `--synonyms` / `--skills` | 可选 |
| `--dir` | 默认 `<DSH_HOME>/capability-router/experts/<id>/` |
| `--force` | 覆盖已存在的同名专家 |
| `--dry-run` | 只打印，不落盘 |

三条硬约束：

1. **必填就必填**：缺一个直接退出（exit 2）。不猜触发词、不编描述——猜出来的措辞会被人直接接受，比生成失败更糟。
2. **写完当场校验**：用同一个 `loadExpert` 读一遍，读不出来就不落盘。
3. **不覆盖**：同名目录存在时要求 `--force`。

`role.md` 是骨架（工作方式 / 边界 / 交付），必须按领域重写。落地顺序：改 `role.md` → 人审 → 重启 DSH（专家包在挂载时扫描）。

## 十三、数据文件

都在 `<DSH_HOME>/capability-router/`（默认 `~/.dsh/capability-router/`）：

| 文件 | 内容 | 写入时机 | 截断 |
|---|---|---|---|
| `config.json` | 用户配置，缺省字段用内置默认值 | 手动 / `saveConfig()` | — |
| `hints.jsonl` | 每次检查点注入一行（`at` + `promptId`） | 注入时 | 超 64 KB 只留后一半 |
| `gaps.jsonl` | 每次落空一行（`at` / `kind` / `text` / `candidates`） | 落空且像派活时 | 同上 |
| `trace.jsonl` | `debug: true` 时每次 pre-step 的现场 | 每步 | 同上 |
| `experts/` | 用户自建或覆盖的专家包 | `tools/forge.mjs` | — |
| `sessions/<id>.json` | 每个会话的阶段、方案确认、用户水平与在场专家 | 打开专家时 | — |
| `runs.jsonl` | 每次 pre-step 的判断（会话 / 阶段 / 命中 / 注入了什么） | 每步 | 同上 |

JSONL 追加是同步写、失败静默——记账失败不能影响注入。

## 十四、与宿主的契约（实现必须知道的）

| 事实 | 出处 |
|---|---|
| `pre-step` 是瀑布，先 `await next()` 再决定追加 | `dsh-agent` 事件定义 |
| `decision.messages` 为空时退回 `payload.messages` | 实测，见 DESIGN 坑 2 |
| 追加的消息**不进会话历史** | DESIGN 坑 3 |
| `payload.messages` 可能为 0 长度（热重载后的实例） | DESIGN 坑 1（`p=0` 不等于没挂钩） |
| 技能目录消息是全量替换、按 digest 去重 | `dsh-tool-skill/lib/index.js:931` |
| provider 按调用方作用域分层，读目录时靠后的层覆盖 | `dsh-skill/lib/index.js:109-120、298-310` |

时序上的一个已知现象：收窄是在 `await next()` **之后**算的，所以目录变化要到**下一步**才反映出来；而角色与缺口是直接追加到 `decision.messages` 的，当步就可见。

## 十六、只读面板（`tools/panel.mjs`）

```bash
npm run panel                  # 127.0.0.1 随机端口，打印地址
npm run panel -- --port 7788   # 固定端口
npm run panel -- --dir D:/skills
```

浏览器打开就三屏，全部只读：

| 区块 | 数据来源 | 回答什么 |
|---|---|---|
| 会话阶段 | `sessions/*.json`，有 `project` 时以 `<项目>/.capability-router/state.json` 为准（v0.20.6） | 哪个会话在项目模式、到哪一步、在场是谁。**镜像过期时以项目为准**——同一个项目被几个会话接手，镜像会各自停在推它的那一刻 |
| 最近 25 句 | `runs.jsonl`（按 `promptId` 折叠，v0.20.3） | 刚才那些步判成了什么、注入了什么；一句多步合并成一行挂 `×N` |
| 缺口队列 | `gaps.jsonl`（按原话聚合） | 哪类活反复没人接、当时怀疑哪两个专家 |
| 技能供给 | 专家包 + `~/.dsh/skills` | 哪个专家的必装技能没装 |

三个端点：`/` 页面（5 秒自动刷新）、`/api/state`（JSON 快照，将来的 client 半边直接吃这个）、`/health`。

### 三件刻意的选择

- **只听 loopback、只读、不写文件**。面板是旁路，挂了不影响插件；远程访问时这个地址指向用户自己的机器，将来 client 半边嵌入时要处理（billion-context 的做法是给一段 `remote_blocked` 文案）。
- **每次请求重新读文件，不做缓存**。面板要显示「刚刚发生的事」，缓存等于骗自己。
- **数据层与渲染层分开**（`lib/panel.js` 出 HTML，`tools/panel.mjs` 出 HTTP）。宿主换 UI 通道时换的是壳，不是这一层——第 8 步的 client 半边就是换壳。

---

### 同一个面板，三种打开方式

| 方式 | 地址 | 谁在用 |
|---|---|---|
| 独立进程 | `npm run panel` → `127.0.0.1:<port>/` | 不启动 DSH 也能看；命令行排查 |
| 宿主路由 | `http://<DSH 的地址>/capability-router/panel` | GUI，同源同端口 |
| client 半边 | 插件详情页那块 + 会话页「编排」tab | 日常看 |

### 两个 iframe 看的不是同一批数据

| 落点 | 地址 | 范围 |
|---|---|---|
| 插件详情页 | `/capability-router/panel` | 全部会话（概览） |
| 会话页「编排」tab | `/capability-router/panel?session=<会话id>` | 只有当前会话 |

会话 id 由 slot 的 `sessionId` 属性传进来（`conversation.view` 的 standardProps 里有它），client 半边把它拼进 iframe 地址，过滤发生在服务端的 `collect(stateDir, { sessionId })`——不是前端隐藏，是根本不读别的会话。

两处刻意的不对称：

- **缺口队列始终是全局的**。`gaps.jsonl` 不按会话记录（它回答的是「哪类活反复没人接」，这在会话之间才有意义），所以单会话视图里也保留，并在标题上标一句。
- **`runs.jsonl` 单会话视图会读更多行再筛**：文件是全局追加的，只看最后 200 行可能一个当前会话的记录都没有。所以按会话视图时先读 5000 行再筛最后 200。

**为什么又做一份路由版**：独立进程的 `127.0.0.1` 在远程访问时指向用户自己的机器（billion-context 专门写了 `remote_blocked` 文案），而宿主路由与 GUI 同源同端口，远程访问天然正确，还免了跨域。数据层是同一份 `lib/panel.js`。

### client 半边：一个 80 行的文件，没有构建步骤

`client/index.js` 就是产物，形状照宿主加载器来（见 `@deepseek-ai/dsh-client-modules`）：

```js
window.__ModuleLoader__.load({
  id: "dsh-capability-router",
  factory: (require) => {
    const React = require("react");   // 宿主提供，不用打包
    function apply(ctx) {
      ctx.slots.inject("plugins.bundle.config", () => ctx.slots.register(
        { name: "plugins.bundle.config", key: "dsh-capability-router" }, Panel));
      ctx.slots.inject("conversation.view", () => ctx.slots.register(
        { name: "conversation.view", id: "capability-router", order: 40, label: () => "编排" }, Panel));
    }
    return { apply, inject: ["slots"] };
  },
});
```

两处 slot 里放的都是一个 iframe，指向 `/capability-router/panel`——不重复实现 UI，面板怎么改都不动壳。

清单三件套（缺一个就加载不上）：

```json
"exports": { "./client": "./client/index.js" },
"dsh": { "client": { "platform": "web" } }
```

`@deepseek-ai/dsh-client-modules` 的 `resolveMeta()` 要求 `dsh.client.platform === "web"` 且能解析到 `exports["./client"]`，否则抛 `declares dsh.client but exports no "./client" bundle`。

## 十七、已知限制

1. **技能只写名字、不校验供给**：专家的 `skills` 是引用，装没装、版本对不对要等人看（下一版补 `npm run doctor`）。
2. **匹配是规则**：词表覆盖不到的说法会落空。落空的句子会被记账，用 `npm run gaps` 看高频缺口——那是补词表还是造专家的判断依据。
3. **不出现在会话历史**：注入只作用于当步上下文。事后回看会话，看不到检查点与角色消息，只能查 `hints.jsonl`。
4. **角色注入还没有 A/B**：检查点那版有对照数据（DESIGN 第十节），角色注入目前只有「确实注入了」的证据，没有「确实改变了行为」的证据。
5. **`level` 只改提示文案，不改专家行为定义**：它进状态卡与闸门文案；`role.md` 是静态文件，同一个专家对新手和老手说的是同一段话。真要做到「同一个人换个讲法」，得按 `level` 生成角色提示词或拆成两套专家包，这一版没做。
6. **方案确认是软闸门**：模型一次都不调 `expert()` 时，`level` 与 `approved` 这两条链完全不生效。宿主没有「拦截工具调用」的钩子，插件只能在 `expert()` 的返回里追加一句话，拦不住模型直接写代码。
