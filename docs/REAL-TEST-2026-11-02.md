## 二、最硬的一条证据：ON 全程 0 次 `expert()` 调用

会话原始记录（`session-b19fbe89.../session.v4.jsonl.zstd`）：

- 工具调用统计里没有 `expert`。`request/header` 里 `expert` 工具是在的——**注册成功了，模型就是没调**。
- `CALL skill` 只有 3 次：`brainstorming`、`frontend-design`、`playwright`。全程只有一个身份（没有换人）。
- `subagent` / `spawn_teammate` / `team_task_*` 都是 0 次。没有派活，也就没有交接。
- `~/.dsh/capability-router/sessions/` 里**没有这个会话的状态文件**——状态文件只在 `expert()` 被调用时才写。所以阶段从第一轮到最后一轮都是 `idle`。
- `runs.jsonl` 里该会话 7 条记录，全是 `"phase":"idle","rout":"miss","injected":["capability-router-hint"]`。

也就是说：**插件在整场里只做了一件事——每轮往用户消息后面贴一段当轮检查点。** 专家目录、`expert()` 工具、状态机、闸门，全部静默。

## 三、"检查点从第一句就接管了"——这句判断是对的，而且能复现

用插件自己的匹配器跑真实首句（`node` 直接 import `lib/router.js` + `lib/gap.js`）：

| 用户原话 | 路由结论 | 最高分 | 像不像一件活 | 缺口提示 |
|---|---|---|---|---|
| 我想做一款Windows记账软件，整体看起来简约大方。 | miss | **0.0** | **false** | **无** |
| 像Apple那样。 | miss | 0.0 | false | 无 |
| 安装包无法安装。 | miss | 0.0 | false | 无 |
| 安装版跟免安装版都无法打开。 | miss | 0.0 | false | 无 |
| 把源码打包吧。 | miss | 0.0 | false | 无 |
| 帮我做个记账软件 | miss | 0.0 | true | 有（但先说"没有干这个的人"） |
| 从零做一个记账应用，要好看 | hit intake | 2.5 | true | — |
| 这个功能帮我验收一下 | hit review | 1.5 | true | — |

两件事同时成立：

1. **所有专家 0 分**。frontend 的触发词是「界面/样式/组件/页面…」，intake 的是「项目/从零/立项/需求…」——真人第一句说的是「做一款记账软件」，一个都不沾。
2. **`looksLikeTask` 也是 false**。`lib/gap.js:12-18` 的任务词表收了「做个 / 做一个 / 想…」，没有「做一款」。所以连那句「要是个新项目，先打开接单专家」的兜底都没触发。

于是第一轮，插件除了通用检查点，一句都没说。后面六轮同理。

这是**词汇表漏词**导致的整条链不点火，不是模型不听话。

## 四、代码层面的因果链（不是模型懒，是设计上就点不着）

### 4.1 状态机无法自举

`lib/index.js:619-626`：

```js
const projectMode = projectState !== undefined && projectState.phase !== "idle";
```

`phase` 只在 `expert()` 的 `onOpen` 里被写（`lib/index.js:525-563`，`lib/state.js:120-127`）。
模型不调 `expert()` → 没有状态文件 → `phase` 永远 `idle` → **项目模式永远不亮**。
而项目模式才是"状态卡 + 闸门 + 收口"的载体。

一句话：**插件把最有价值的部件设成了"需要被它想帮助的那个模型主动开启"的开关。**

### 4.2 检查点是分类器，不是调度器

`lib/index.js:100-108` 的分支只有三种：提问 / 命令 / 报告。
「命令」那一条写的是 **"有一个会改变实现方向的黑洞就问……没有就开工"**——它直接授权了单人开工，从没提"先去接单""先确认需求""干完要审"。

ON 会话第一轮模型的推理原文：

> 同时能力路由说：命令类，有一个会改变实现方向的黑洞就问一个，附推荐答案。

它照做了：问了一个技术栈，然后开工。**检查点起作用了，起作用的方向是"一个人干"。**

### 4.3 三套话术在对喊，最近的那套赢

- `INTAKE_TEXT`（`lib/index.js:87-93`，系统提示 5K 位）：需求有空白先问清楚。
- `HINT_TEXT`（`lib/index.js:100-108`，每轮紧跟用户消息）：问一个，没有就开工。
- `experts/intake/role.md`：先问，再写 REQUIREMENTS.md + TASKS.md，然后分派。

三份都是"用户角色消息"，但检查点**离用户那句话最近**，权重最高。实测里模型引用的是检查点，不是目录，也不是角色。

`docs/ARCHITECTURE.md:184-190` 已经预判了这个风险（"检查点降级……避免两条协议对喊"），但只处理了"项目模式 vs 检查点"这一对，没处理"检查点 vs 接单专家"这一对。

### 4.4 目录常驻 ⇒ 规则注入被关掉 ⇒ 只剩模型自己一条路

`lib/index.js:630`：

```js
if (resolved.role && !resolved.catalog && verdict.kind === "hit" && ...)
```

默认 `catalog: true`，所以 `role` 注入**永不生效**。设计上说得通（v2 把选择权交回模型），但代价是：**专家机制从"插件推"变成"模型拉"，且没有任何兜底**。模型不拉，就一次都不发生。

### 4.5 没有收口闸门

`lib/state.js:120-127` 里，`build → review` 只在 `expert("review")` 被打开时发生。没有任何一处规定「声称交付前必须过 review」。
`gateNote`（`lib/state.js:159-168`）只有两条提醒：spec 期别开工、idle 期别审查。**没有"该收口了"这一条**。

更糟的是检查点的第三分支：「报告（是继续）：接着做，别重新评估已经定下的事。」——在"把源码打包"这种交付回合，这句话是反向施力。

### 4.6 `docs/ARCHITECTURE.md` 里有的东西，代码里没有

设计稿 74 行写的是：

```text
intake   接单：把模糊需求收敛成需求与任务卡。任何项目的第一站。
```

`lib/catalog.js:22` 实际渲染的只有 `名字（id，kind）：description`。「任何项目的第一站」这句**没进系统提示**。

设计稿的阶段表有 `intake / spec / build / review / deliver` 和 `specConfirmed`；`lib/state.js:15` 只有 `idle / spec / build / review`，没有 `deliver`，没有 `specConfirmed`。**收口和确认这两个字段，在实现里不存在。**

## 五、缺审查的真实代价：两次都没跑起来，但只有 OFF 找对了原因

两个成品，用户都反馈打不开：

- ON：`安装包无法安装` → `安装版跟免安装版都无法打开` → `把源码打包吧`。
- OFF：`不管是安装版还是便携版，都无法使用啊` → `双击 release\win-unpacked\轻账.exe，没有窗口` → `把源码打包`。

区别在归因：

- **OFF 的 README 写对了原因**：这台机器开着 VBS + HVCI + WDAC 代码完整性策略，未签名 Electron 主程序在加载阶段被拦，退出码 `0x80000003`；给出了浏览器 app 模式的绕法。
- **ON 的 README 写的是"路径不能含中文，Electron 会 exit 3 秒退"**——一个听起来合理、但与本机实际拦截机制无关的结论。用户照它做，问题依旧。

ON 这一路还有 33 次截图、3 套 mockup、`tools/test-db.mjs` 的数据层测试——**验证做到了"数据层 + 视觉层"，没做到"成品能不能启动"这一层**。`verification-before-completion` 恰好就是干这个的，而它挂在 `review` 专家的 `skills` 里，review 从没上场。

这就是"审查缺席"的具体价钱：不是代码难看，是**根因判断错了，用户白折腾两轮**。

## 六、回答你的问题：检查点该不该并进接单专家

**不该合。但你的直觉指对了病灶——只是刀要下在别处。**

理由三条：

1. **两者生命周期不同**。检查点是"每轮都发生"的，接单专家是"一个阶段发生一次"的。合并之后，第一轮之后就没有任何东西每轮提醒了——而这恰好是插件目前唯一真正生效的部件（实测 7 轮全中，模型确实引用了它）。
2. **删掉检查点 ≠ 接单专家接管**。接单专家要靠 `expert("intake")` 才会出现，而 ON 全场 0 次调用；再把检查点删了，首轮就是彻底的静默——连"问一个黑洞"都不会有。实测会更好吗？更可能是更差。
3. **真正的问题是检查点缺一个分支，不是它存在**。它现在回答"这是什么"，不回答"接着找谁"。

所以正确的动作是：**给检查点加"接单 / 收口"两个分支，并让状态机可以从检查点这一侧被点火。**

```text
提问  → 直接答
命令  → 新活（新项目 / 新功能）→ expert("intake") 开场；改 bug → expert("debug")
报告  → 继续；但如果这轮要交付 / 声称做完 → 先 expert("review")
```

接单专家不并进检查点，而是**挂在检查点的一个分支上**——检查点是调度台，接单专家是调度台叫来的第一个工位。

## 七、改进清单（按性价比排）

### P0-1 检查点加两个分支（改文案 + 改 `HINT_TEXT`）

`lib/index.js:100-108` 的「命令」改成：

> **命令**（要动作）：这是一个新项目 / 新功能（不是修一个既有 bug）→ 先 `expert("intake")`，让它把需求和任务卡落盘，再按它的分派往下走；是修 bug → `expert("debug")`。只有一个会改变实现方向的黑洞才问，一次一个，附推荐答案。

「报告」改成：

> **报告**（是继续）：接着做。**但这轮如果要交付、要说"做完了/可以用了"，先 `expert("review")` 过一遍验收标准**，没证据不算完。

### P0-2 让状态机能自举（插件先点火，模型再决定要不要熄）

`lib/index.js:618-626` 之前加一条：非项目模式下若 `verdict.kind === "miss"` 且 `looksLikeTask(text)`，**直接写 `phase = "spec"` 到会话状态**（`project` 留空，等项目路径出现再挂）。

理由：项目模式现在是"模型 opt-in"，而模型不知道自己需要它。让插件根据"这是不是一件新活"先落到 spec，状态卡下一轮就自己出现——错了模型可以不管，代价只是多一行字。

配套：`state.js:124` 的 `openExpert` 不再需要靠 `expert()` 才能进 spec。

### P0-3 匹配器和任务词表补最常见的说法

- `lib/gap.js:12-18` 加：`做一款 / 做一个 / 想做 / 要个 / 弄个 / 开发 / 搞一个 / 整套 / 从零`。
- `experts/intake/expert.yml` 的 `triggers` 加：`做一款, 做一个, 开发, 搭一个, 软件, 应用, 系统, 工具`（intake 是"新活"的承包方，不是"立项"术语的承包方）。
- 补一条回归测试：`test/route.mjs` 里把本次 7 句原话断言成 `miss + task=false` 的现状，改成断言「必须落到 intake」。

### P1-1 落空时的第一句话改成 intake，别先喊缺人

`lib/gap.js:69-72` 现在先说「现有专家：……都不是干这个的」，再说"可以先打开接单专家"。对一个全新项目，第一句是错的（有 frontend/backend，只是还没拆）。
改成：`miss + looksLikeTask` → 「这是件新活，先 expert("intake") 拆成任务卡；拆完发现确实没人接的部分再说缺人。」

### P1-2 交付闸门（这是本次损失最大的地方）

`present` 之前 / 声称完成时，若 `phase === "build"`，注入一条：

```text
【能力路由 · 收口】还没有审查记录。按 REQUIREMENTS.md 的验收标准逐条核对，
或 expert("review") 走一遍；没跑起来的东西别写"完成"。
```

`docs/ARCHITECTURE.md` 里 `deliver` 阶段和 `specConfirmed` 字段要么实现，要么从文档里删掉——现在文档承诺的收口，代码里不存在。

### P1-3 把 `gateNote` 变成"挡一下"而不是"说一句"

`lib/state.js:159-168` 目前只在打开专家时返回一段话。既然 `expert()` 是我们自己的工具，**在 spec 未确认时打开 worker，可以让工具返回 `isError:true` + 说明**，而不是纯提示。这样至少"跳过需求确认直接开工"要多走一步。

### P2-1 三套话术收敛成一套

`INTAKE_TEXT`（5K 位系统提示）和 `HINT_TEXT`（每轮）说的是同一个协议的两半，措辞不一致。建议：系统提示只留"目录 + 三条规矩"，协议全部交给检查点一个地方维护，避免同一件事两种说法各自演化。

### P2-2 观测口径：现在量不出"插件有没有被用上"

`runs.jsonl` 每轮记了 `phase / rout / injected`，但没有 `expertOpened`、没有 `phaseAfter`、没有"这一轮交付了没"。本次复盘是靠翻会话原始记录才确认"0 次 expert()"的。

建议每轮加三个字段：`expertsInPlay`（从状态文件读，没有就空数组）、`delivered`（本轮有没有 `present` / 写 `release/`）、`verified`（本轮有没有跑过构建或启动）。面板直接出「专家使用率 / 审查覆盖率」两个数。

### P2-3 缓存代价：ON 的两次折叠命中率 34.5% / 39.0%，OFF 55.7%

检查点是**每轮在用户消息后插入一条新的 user 消息**，等于每轮把后面的前缀全部推倒一次。ON 总体还是更便宜（少 31% 输入），但如果把检查点改造成"固定位置、内容不变的 system-reminder"（或干脆并入稳定前缀、只在分支判定变化时换文案），折叠成本还能再降一截。这条要先做 A/B 再动，别凭直觉改。

### 新增的两条机制（清单里没有，但复盘指向它们）

**入口让位**（`lib/router.js`）：`kind: intake` 的专家在有别的专家过线时自动排到后面，且不参与 `ambiguous` / `multi` / 主次判定。这是 P0-3 的结构化解法——不给 intake 加词会把「做一款记账软件」判成落空，加了词它又会抢「做个报价单」。让位规则让两件事同时成立。回归：a/b/c 三集仍 100%，且「把这个需求文档改成给老板看的版本」从错判 `intake`(4.0) 改回 `docs`(3.5)。

**主次提示**（`lib/gap.js` 的 `secondaryText`）：头名明确但次名仍明显过线时，多说一句「副的那部分也得有人管」，并冠上 `capability-router-secondary`。真实用例里「记账软件 + 说明 PPT」这种句子，旧逻辑只交一半。

### 为什么 P0-2 没让插件自动写阶段

`docs/ARCHITECTURE.md` 的第一原则是「插件不猜阶段，只读事实」。让插件根据一句话的匹配结果自己写 `phase = "spec"`，就是把「猜」写进状态机——猜错的后果比不猜更重（用户一句「这个 bug 修一下」会把项目推进 spec）。

所以换了个位置：**在 `expert()` 的返回里说话**。`idle` 阶段第一次打开 worker 时，`gateNote` 返回「还没接单，先 `expert("intake")`」。它不猜、不写状态、不拦截，但把「你跳过了接单」这件事摆到模型眼前——真实用例里缺的正是这一句。

### 为什么 P1-3 没改成 isError

`expert()` 返回 `isError: true` 会让「打开专家」这个动作本身失败，模型要么重试要么放弃，两个结果都比「拿到专家 + 一句提醒」差。闸门的定位是**把事实摆出来**，不是拒绝服务。真要硬拦，得包 `ctx.tools.register` 的 wrapper，那是 v2.1 的事，而且会跟用户自己的工具调用打架（这一条在 ARCHITECTURE 里已经写过）。

### 为什么 P2-3 没动缓存

检查点改稳定前缀是**实验**，不是修复：改完要么更便宜（前缀可命中），要么更贵（每轮都带一段没用的分支文本）。在拿出 A/B 数据之前动它，等于拿真实会话做无对照实验。留作下一轮。
